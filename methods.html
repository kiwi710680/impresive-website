Methods & technology

A reproducible path from question to evidence

IMPRESIVE combines fit-for-purpose feasibility, common definitions, flexible standardization, quality validation, distributed execution, and contextual interpretation.

Eight-step pipeline

The IMPRESIVE study workflow

  1. Research question

    Translate a clinical, policy, or regulatory need into the target population, exposure, comparator, outcome, follow-up, and time zero.

  2. Feasibility & fit for purpose

    Assess whether each data environment can answer this specific question. Full database conversion is not a prerequisite for every study.

  3. Protocol & variable definition

    Align the common protocol, statistical analysis plan, code lists, variable specifications, and output formats.

  4. Standardization & common data model

    Use OMOP, Sentinel-like, or another governed structure to create a common analytical interface appropriate to the local setting.

  5. Quality validation

    Check structural conformance, completeness, plausibility, cohort and variable behavior, and analytical consistency.

  6. Distributed execution

    Approved partners run common programs locally and document adaptations, exceptions, and limitations.

  7. Evidence integration

    Bring together permitted aggregate outputs while preserving site-level context and distinguishing implementation issues from true differences.

  8. Visualization & interpretation

    Present country-specific and integrated findings with transparent definitions, uncertainty, and contextual explanations.

    Fit-for-purpose standardization

    One interface does not require one identical workflow

    The programme experience compares two common-data-model routes with different strengths and implementation demands.

    Stronger semantic standardization

    OMOP CDM

    • Standardizes structure and semantic vocabularies.
    • Required extensive vocabulary mapping and greater computing resources in the implementation described by the programme.
    • Required ETL development with dummy data outside the secure environment before transfer into that environment.
    • Requires locally maintained mappings where source codes have no established crosswalk.
    Source-preserving operational fit

    Sentinel CDM

    • Emphasizes structural standardization while retaining more source terminology.
    • Manages vocabulary differences through study definitions and site-level code lists.
    • Was easier to implement within the secure SAS environment described by the programme.
    • Still requires documented local adaptation, including drug-strength and source-code handling.
    Local adaptation is part of the method.

    Structural conversion alone is not enough. Date construction, drug information, source-specific code mapping, and variable definitions must be documented and validated.

    Quality assurance

    Three canonical dimensions, then study-specific validity

    General common-data-model quality checks are distinct from validating whether a specific cohort or analysis behaves as intended.

    1

    Conformance

    Structure, formats, and identifiers.

    2

    Completeness

    Domain and variable availability.

    3

    Plausibility

    Values, dates, and clinical patterns.

    4

    Study-specific validity

    Cohorts, variables, frequencies, and analytic outputs compared with the protocol and source context.

    Distributed by design

    The analytic program travels—not the source data

    Local partners work within their approved secure environments. Only outputs permitted by local governance are returned for review and integration.

    What is shared

    Common question, protocol, specifications, analysis program, QA logic, and agreed output structure.

    What stays local

    Person-level source data, local access controls, data-owner approvals, and environment-specific implementation detail.

    What returns

    Permitted aggregate results, QA summaries, implementation notes, and limitations needed for interpretation.

    Method resources

    Release resources only after content and ownership are verified

    The public site can explain the ETL process, structural mappings, quality framework, and approved evidence data. Protocols, code lists, QA tools, and analytic code need separate owner, version, governance, and maintenance review before public release.
